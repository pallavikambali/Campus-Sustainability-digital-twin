PHASE 2 — FUNCTIONAL DIGITAL TWIN

Build an interactive 2D campus representation using actual campus zones already available in the database or backend.

Requirements:

- Each zone must be clickable.
- Show energy, water, occupancy and waste readings for the selected zone.
- Calculate zone status using the actual configured thresholds.
- Green means normal, yellow means warning, red means critical.
- Provide status filters and a clear colour legend.
- Refresh the display from backend data.
- Display a timestamp indicating when the readings were last updated.
- Handle missing readings without inventing measurements.
- If the backend is unavailable, show a visible error instead of silently displaying fake live data.

Selecting a zone must show its details. Filters must change the visible zones. Status indicators must reflect the actual readings and configured thresholds.

PHASE 3 — FUNCTIONAL WHAT-IF SIMULATOR

Implement a working simulator with inputs for:

- Energy reduction percentage.
- Water reduction percentage.
- Occupancy change.
- Waste reduction percentage.
- Optional sustainability interventions supported by the project.

Every input change must update the results using real calculations.

Required outputs:

- Baseline consumption.
- Projected consumption.
- Energy saved in kWh.
- Water saved in litres.
- Waste reduction with clearly defined units.
- Estimated cost savings in ₹.
- Estimated CO2 emissions reduction.
- Before-and-after charts.
- Changes in predicted zone status and alerts.

Implementation rules:

1. Use actual baseline readings from the backend.
2. Validate inputs and reject invalid values.
3. Prevent negative consumption and unrealistic percentages.
4. Use configurable tariffs and emissions factors.
5. Display assumptions and calculation units.
6. Use one consistent calculation method across cards and charts.
7. Keep simulations separate from actual measurements.
8. Do not send simulation values to production readings or overwrite database records.
9. Reset must restore the original baseline.
10. If a baseline is unavailable, disable calculations and explain what data is missing.

Implement and test the calculation functions rather than using arbitrary numbers or random results.

PHASE 4 — COMPLETE INCIDENT LIFECYCLE

Implement this exact workflow:

Detection → Recommended Action → Action Addressed → Verification → Resolved or Reopened.

Each incident should have:

- Unique ID.
- Zone ID.
- Resource or metric.
- Observed reading.
- Configured threshold.
- Severity.
- Recommended action.
- Creation timestamp.
- Current lifecycle status.
- Action and verification timestamps where appropriate.

Functional requirements:

1. Detect abnormal readings using existing backend rules.
2. Persist new incidents in the existing database.
3. Prevent duplicate active incidents for the same ongoing condition.
4. Allow an authorised user to mark an action as addressed.
5. Verify the latest available reading against the configured threshold.
6. Resolve an incident only when the latest valid reading satisfies the recovery rule.
7. If the condition remains abnormal, keep the incident unresolved and explain why.
8. If a previously resolved condition becomes abnormal again, create or reopen an incident according to the existing incident policy.
9. Maintain an incident history.
10. Show accurate status changes in the interface after successful API responses.
11. Handle repeated requests safely and prevent accidental duplicate records.

Do not treat clicking the Addressed button as proof that the problem has been fixed. Do not mark an incident resolved merely because the user clicked Verify. Verification must use actual stored readings or explicitly identified simulated readings from the existing simulator.

If there is no new reading available, show “Unable to verify: no current reading available.”

PHASE 6 — IMPACT CALCULATIONS

Use consistent, documented formulas.

Energy savings = Baseline energy − Projected energy.

Water savings = Baseline water − Projected water.

Estimated cost savings = Energy savings × configured electricity tariff + Water savings × configured water tariff.

Estimated CO2 reduction must use documented, configurable emissions factors and consistent units.

Waste reduction must compare the baseline and projected quantities using the same unit.

Do not mix instantaneous power in kW with energy in kWh. Account for the measurement period when necessary.

Do not invent measured savings, carbon reductions, tariffs or campus statistics. Label projections as estimates and show the assumptions used.

DIGITAL TWIN

- Warning readings produce warning status.
- Critical readings produce critical status.
